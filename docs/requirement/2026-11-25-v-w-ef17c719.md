# Requirement: Borough-to-borough trip and revenue flows for Q1 2024

## Ask

Leila Haddad, Mobility Planning Lead, for the city:

> "The city asked how much of our traffic crosses borough lines. For each month of Q1 2024, I need the trips and the revenue from each borough to each borough, and the share of trips that leave the borough they started in."

Consumer: Mobility Planning and, through them, the city. The answer is one new table in the project, at borough grain, monthly, covering Q1 2024.

What the data says about the ask, so the numbers below are not read as findings: Q1 2024 holds 95,958 billable trips for $2,629,185.82 of billable revenue from 2024-01-01 to 2024-03-31 inclusive. Borough-to-borough, those trips fall into 122 pairs that carry traffic. With both ends placed in a named borough — the population `R-04`'s share is computed over — 11,472 of 94,958 trips (12.08%) end in a borough other than the one they started in.

## Requirements

- [ ] `R-01` One boundary table with one row per (calendar month, origin borough, destination borough) for Q1 2024, over the full grid of the eight borough values `dim_zone` carries, not only the pairs that carried a trip — accept when the table returns 192 rows and grouping it by (month, origin borough, destination borough) yields 192 distinct groups — source: request; user answer on grid ("Full grid, zero rows included")
- [ ] `R-02` The table reports billable trips and revenue per pair, revenue being the summed trip total — accept when the table's `sum(trip_count)` is 95,958 and its `sum(revenue)` is 2,629,185.82, i.e. equal to `fct_trip` restricted to the reporting window and `is_billable`, and when each month's `sum(trip_count)` matches an independent recount for that month — source: `docs/adr/0003-billable-trip-definition-and-where-it-applies.md` ("A new revenue or flow mart applies the rule"); request
- [ ] `R-03` No minimum-traffic floor is applied at this grain: every borough pair that carries a billable trip is published, however thin — accept when the 66 pairs under 25 trips (253 trips) are present in the table and `sum(trip_count)` therefore stays 95,958, where a 25-trip floor would have removed them — source: user answer on floor ("No floor on this table"); the floor's stated scope is `agg_od_flow_matrix` in `docs/adr/0017-published-flows-have-a-25-trip-floor.md`
- [ ] `R-04` For each month and origin borough the table carries the share of that borough's trips that end in a different borough, computed over trips whose destination resolves to a borough, with the denominator and the excluded unresolved-destination count published beside it — accept when, for every (month, origin borough) row, `crossing_trip_count / resolved_destination_trip_count` reproduces an independent recomputation, and `crossing_trip_count + same_borough_trip_count = resolved_destination_trip_count` — source: user answer on crossing share ("Resolved ends only")
- [ ] `R-05` Trips touching a zone the TLC cannot place in a borough are retained, flagged as their own groups, never dropped, remapped or folded into a named borough — accept when the `Unknown` and `N/A` borough values appear as their own origin and destination groups and the 1,000 billable trips that touch an unresolved zone are all counted in the table — source: `docs/adr/0012-unresolved-zones-are-retained-and-flagged.md`; `CONTEXT.md` "Unresolved zone"
- [ ] `R-06` The table ships as a boundary relation with what a boundary relation owes: a contract, tests and a design record, and it is mapped into the canonical model — accept when its ODCS contract passes `odcs.py check`, its dbt tests and the singular tests that hold `R-01` to `R-05` pass on a build at the shipping commit, and the Ossie document under `logical-model/` names the relation — source: `repo-map.json` `modules.contracts` and `modules.logical_model`; `docs/adr/0225` boundary is declared on the gold relations

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain | One row per (calendar month, origin borough, destination borough); month is the calendar month of the trip's pickup date, which is the date every other mart reports a trip on | request (`CONTEXT.md` "Date", "Reporting window"); `fct_trip.pickup_date` |
| Period boundary | Q1 2024 = pickup date from 2024-01-01 up to but excluding 2024-04-01, the project's reporting window | request; `transformation/dbt_project.yml` `report_start`/`report_end` |
| Edge periods | Not applicable: the data window is exactly 2024-01-01 to 2024-03-31, so no month of Q1 is cut short (checked against `fct_trip` min/max pickup date) | repository |
| Population | Billable trips only, inside the reporting window, both service types; a non-billable trip is not traffic anyone paid for | `docs/adr/0003-billable-trip-definition-and-where-it-applies.md` |
| Revenue measure | The trip total, summed per pair, as `agg_od_flow_matrix` and `mart_daily_zone_revenue` report it | request ("revenue"); existing models |
| Rows with no traffic | Emitted with zero trips and zero revenue, so every borough's row set is identical every month and an absent pair is never confused with a missing report | user answer on grid ("Full grid, zero rows included") |
| Minimum-traffic floor | None at this grain; ADR 0017's 25-trip floor keeps its stated scope, the published zone-pair matrix | user answer on floor ("No floor on this table") |
| Crossing share — numerator | Trips from the origin borough whose destination borough differs from it | request; user answer on crossing share |
| Crossing share — denominator | Trips from the origin borough whose destination resolves to a borough; trips ending in `Unknown` or `N/A` are excluded from both numerator and denominator and their count is published beside the share | user answer on crossing share ("Resolved ends only") |
| Crossing share — unresolved origin | No share: a row whose origin is `Unknown` or `N/A` carries null, because a zone the source cannot place is not "the borough they started in" and no crossing can be attributed to it | derived from the answer on crossing share; `CONTEXT.md` "Unresolved zone" |
| Unresolved zones | Retained as their own borough groups on both roles, in the trip counts and revenue, and excluded only from the crossing-share ratio | `docs/adr/0012-unresolved-zones-are-retained-and-flagged.md`; user answer on crossing share |
| Cross-borough edges | `EWR` is a resolved borough value in `dim_zone` (reporting region "Out of State"), so a trip between it and a New York borough is a crossing; it is not treated as unresolved | repository (`core.dim_zone` borough list) |
| Unmatched zone keys | A trip whose zone key matches no `dim_zone` row is kept and grouped as unresolved rather than dropped, and the zero-row grid means a pair losing every trip still reports a row | playbook default ("Keep every row"); `docs/adr/0015-unmatched-dimension-keys-stay-null.md` |
| Coverage | Trips and revenue are present on every row, so no coverage count is added for them; the crossing share carries its denominator and its excluded unresolved count on the row | playbook default ("Publish the count") |
| Reuse | Not built on `agg_od_flow_matrix`: that surface is the zone-pair matrix truncated by ADR 0017's floor, so its trips are a subset (68,513 of 95,958) and summing it would undercount every thin cross-borough pair this table exists to show. Built from `fct_trip` with `dim_zone` joined twice, which is what the matrix itself does | user answer on floor; repository (`transformation/models/marts/agg/agg_od_flow_matrix.sql`) |
| Extended scope | No schedule is requested, so no `orchestration` kind; the contract, the semantic-model binding and any ontology mapping are built from the boundary model and stay in `transformation` | playbook ("Extended scope") |

## Out of scope

- `agg_od_flow_matrix`, `mart_daily_zone_revenue`, `agg_weather_demand_daily`, `fct_trip`, `dim_zone` and every other published relation: none may change, including ADR 0017's floor on the zone-pair matrix.
- Ingestion and the source systems: no new source, no pipeline change.
- Zone-pair and reporting-region grain answers: this table is borough grain only.
- Filtering, mapping or repairing unresolved zones, and any change to how the TLC zone lookup is loaded.

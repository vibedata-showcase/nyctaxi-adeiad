# Requirement: R9 · zone revenue

## Ask

Ravi Menon, who owns the finance reports:

> "Finance reads the daily zone revenue report every morning. Operations keeps its own daily figures by zone, so we pay for two builds that should give the same answers. Please build our report from the operations figures, so that there is one source. No number in our report may change. Before we accept a change, we run our usual check: for Q1 2024 the report must show 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips and 337,711.05 revenue for JFK Airport."

The report is `finance.mart_daily_zone_revenue`; the finance team reads it every morning, and the semantic layer publishes `billable_trip_count` and `billable_revenue` off it.

The operator's own trip records cannot carry this report: `ops_raw.trip_assignment` holds 4,574 of Q1's 95,958 billable trips (4,503 billable, 122,139.20 revenue), yellow only, because the operator runs part of the city's fleet and no green trips. Asked which figures the report should be built from, the owner chose one build over all trips, with the billable measures carried beside the all-trip ones ([ADR 0018](../adr/0018-daily-zone-revenue-covers-every-billable-trip.md)).

## Requirements

- [ ] `R-01` The zone-day aggregation exists once: `finance.mart_daily_zone_revenue` reads the single daily-by-zone build instead of aggregating `fct_trip` itself — accept when the compiled model selects from that relation and no `count`/`sum` over `fct_trip` remains in it — source: request ("two builds that should give the same answers"), user answer, [ADR 0018](../adr/0018-daily-zone-revenue-covers-every-billable-trip.md)
- [ ] `R-02` The report's population is unchanged: every billable trip of both fleets inside the reporting window, one row per pickup zone and trip date, and a zone-day with no billable trip stays out rather than appearing as zero — accept when Q1 2024 gives 7,961 rows, 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips with 337,711.05 revenue for JFK Airport — source: request ("No number in our report may change", the Q1 2024 check), [ADR 0018](../adr/0018-daily-zone-revenue-covers-every-billable-trip.md)
- [ ] `R-03` Every published measure is unchanged at every zone-day: `trip_count`, `fare_revenue`, `tip_revenue`, `surcharge_revenue`, `toll_revenue`, `total_revenue` — accept when a per-row comparison of the rebuilt report against the figures it publishes today shows zero key and zero value differences across all 7,961 zone-days of Q1 2024 and across the whole window — source: request ("No number in our report may change")
- [ ] `R-04` The report's published shape and contract are unchanged: the same eleven columns with the same types, the same grain and the same key, contract still enforced — accept when the dbt contract build passes with the column set unchanged and the ODCS contract check reports no schema change — source: repository (`contracts/finance/mart_daily_zone_revenue.odcs.yaml`, `transformation/models/marts/finance/_finance.yml`)
- [ ] `R-05` The daily-by-zone build gains the billable measures and its existing all-trip measures keep their meaning and their values — accept when its Q1 2024 all-trip totals remain 7,997 rows, 97,184 trips and 2,597,120.92 revenue, and its `trip_count` still counts every trip, billable or not — source: repository (`agg.agg_trip_zone_daily`, its contract and its Ossie binding), user answer
- [ ] `R-06` The report's published meaning is unchanged: `billable_trip_count` and `billable_revenue` still bind to `finance.mart_daily_zone_revenue` with the same content filter — accept when the semantic-model validate, coverage and suppliers gates pass and the semantic tests return no rows — source: repository (`logical-model/nyc_taxi_analytics.ossie.yaml`, LTS7), [ADR 0003](../adr/0003-billable-trip-definition-and-where-it-applies.md)

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of `mart_daily_zone_revenue` | One row per pickup zone and trip date; key `(trip_date, pickup_location_id)` | repository: the model's SQL and its contract; unchanged by this intent |
| Edge periods | Not applicable: the report is at day grain, and the data covers the whole reporting window 2024-01-01 to 2024-03-31, so no period is cut short | repository: `report_start`/`report_end` and the window's first and last pickup dates |
| Population of the report | Every billable trip of both fleets inside the reporting window; not restricted to fleet-attributed trips; a zone-day with no billable trip is absent | user answer ("One build over all trips"); [ADR 0018](../adr/0018-daily-zone-revenue-covers-every-billable-trip.md) |
| Metric definitions of the report's measures | `trip_count` counts billable trips; each revenue measure sums its own amount over those trips | repository: the model's SQL, unchanged; [ADR 0003](../adr/0003-billable-trip-definition-and-where-it-applies.md) |
| Coverage | `trip_count` stands beside every measure, and every published row carries all six measures; no new measure is added | playbook default (publish the count); already published |
| Reuse | The report is built on the existing daily-by-zone build, `agg.agg_trip_zone_daily`, extended with billable measures, rather than recomputing the grouping from `fct_trip` | user answer |
| Unmatched and null keys | Unchanged: the report resolves each zone through `dim_zone`, so an unresolved zone joins like any other and no trip is dropped for it | repository: the model's join; [ADR 0012](../adr/0012-unresolved-zones-are-retained-and-flagged.md) |
| Extended scope | Not applicable: the intent adds no schedule, so no `orchestration` kind; the contract and semantic deliverables ride with the model | playbook (never asked) |

## Out of scope

- The operator's pipelines, the `ops_raw` tables and the simulated operator data.
- Any column added, removed or retyped on `finance.mart_daily_zone_revenue`; a change to its published shape is a separate, breaking decision.
- The values of published models this intent does not name: the other finance marts, the operations marts, and the existing columns of `agg.agg_trip_zone_daily`.
- A report or dashboard artifact: the report is the mart, and no separate report exists in the repository.

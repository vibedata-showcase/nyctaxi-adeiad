# Requirement: LFQ 2

## Ask

Ravi Menon, who owns the finance reports:

> Finance reads the daily zone revenue report every morning. Operations keeps its own daily figures by zone in the agg schema, so we pay for two builds that should give the same answers. Please build our report from the operations figures, so that there is one source. No number in our report may change. Before we accept a change, we run our usual check: for Q1 2024 the report must show 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips and 337,711.05 revenue for JFK Airport.

The report is `finance.mart_daily_zone_revenue`; the operations figures are `agg.agg_trip_zone_daily`. The result is consumed by the finance team's morning report.

Measured against the Domain today:

| Q1 2024 | rows | trips | revenue | JFK trips | JFK revenue |
| --- | --- | --- | --- | --- | --- |
| `finance.mart_daily_zone_revenue` (as shipped) | 7,961 | 95,958 | 2,629,185.82 | 4,120 | 337,711.05 |
| `agg.agg_trip_zone_daily` (as shipped) | 7,997 | 97,184 | 2,597,120.92 | 4,261 | 329,766.06 |

`agg_trip_zone_daily` counts every in-window trip, and carries only whole-population revenue: it has no billable-only measure, no fare, tip, surcharge or toll revenue, and no `reporting_region`. The difference between the two relations is exactly the non-billable trips (`core.fct_trip` Q1 2024: 97,184 trips, of them 95,958 billable; 2,597,120.92 over all trips against 2,629,185.82 over billable ones). A report that reads the operations figures as they stand therefore changes every number, so the request cannot be met without the operations aggregate gaining the billable-only measures the report publishes.

## Requirements

- [ ] `R-01` `finance.mart_daily_zone_revenue` is built from `agg.agg_trip_zone_daily` and reads no other relation, so the billable rule and the zone aggregation are computed once — accept when the model's compiled SQL names `agg_trip_zone_daily` and no other `ref()`/`source()`, and the dbt graph shows no direct edge from the mart to `core.fct_trip` or `core.dim_zone` — source: request
- [ ] `R-02` No number in the report changes: every cell of the shipped report is reproduced — accept when a full outer join of the rebuilt and the pre-change `finance.mart_daily_zone_revenue` on `(trip_date, pickup_location_id)` returns 0 rows, with every one of the 11 columns compared — source: request ("No number in our report may change")
- [ ] `R-03` The Q1 2024 total is 95,958 trips and 2,629,185.82 revenue — accept when `sum(trip_count)` and `sum(total_revenue)` over `trip_date` in 2024-01-01…2024-03-31 return exactly those two values — source: request
- [ ] `R-04` The Q1 2024 JFK Airport total is 4,120 trips and 337,711.05 revenue — accept when the same query filtered to `zone_name = 'JFK Airport'` returns exactly those two values — source: request
- [ ] `R-05` The report keeps its 11 published columns with their published names and types (`trip_date`, `pickup_location_id`, `borough`, `zone_name`, `reporting_region`, `trip_count`, `fare_revenue`, `tip_revenue`, `surcharge_revenue`, `toll_revenue`, `total_revenue`) and its grain of one row per pickup zone and trip date, publishing a row only where the zone-day has at least one billable trip — accept when the rebuilt relation's columns and types match the pre-change relation exactly, its grain is unique, and no zone-day with zero billable trips appears — source: request + `contracts/finance/mart_daily_zone_revenue.odcs.yaml` + user answer
- [ ] `R-06` `agg_trip_zone_daily` carries the measures the report publishes, at its own zone-day grain: the billable-only trip count, fare, tip, surcharge and toll revenue and total revenue, and `reporting_region` — accept when each column exists with the stated type and the billable-only total revenue over Q1 2024 equals 2,629,185.82 — source: request (the report must be buildable from these figures with no number changing) + repository (the columns the mart publishes)
- [ ] `R-07` `agg_trip_zone_daily`'s existing columns keep their published meaning and values: `trip_count` stays the count of all in-window trips and `total_revenue` stays the sum over all of them — accept when a row-level comparison of the 14 existing columns against the pre-change relation returns 0 differences over the reporting window — source: repository (`_agg.yml` describes both as population-wide; the relation has an active contract and semantic-layer bindings)
- [ ] `R-08` `agg_trip_zone_daily` keeps its grain of one row per pickup zone and date, and keeps every in-window zone-day — accept when its row count and grain uniqueness over the reporting window are unchanged — source: repository
- [ ] `R-09` The billable rule is applied in exactly one place on this path, inside the reporting window — accept when the finance mart's SQL contains no `is_billable` predicate and the aggregate's billable measures are computed with `filter (where is_billable)` before aggregation — source: request ("so that there is one source") + ADR 0003
- [ ] `R-10` The finance mart's enforced contract still passes and its committed ODCS contract needs no column change — accept when `dbt build --select mart_daily_zone_revenue` reports its contract tests green and the contract's property list matches the relation — source: repository (`contract: {enforced: true}`, `contracts/finance/mart_daily_zone_revenue.odcs.yaml`)
- [ ] `R-11` ADR 0003 is amended in this change so its list of gold marts that apply the billable rule names `agg_trip_zone_daily` and no longer names `mart_daily_zone_revenue`, the billable definition itself unchanged — accept when the ADR's text and its affected-designs links agree with the shipped models and `python3 .github/scripts/adr_lint.py` exits 0 — source: user answer

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of `mart_daily_zone_revenue` | One row per pickup zone and trip date | existing model + request |
| Edge periods | not applicable — the mart is at daily grain and the reporting window (2024-01-01 to 2024-04-01) covers every day of the data in full (first trip date 2024-01-01, last 2024-03-31), so no period is cut short | repository (query over `core.fct_trip`) |
| Population: zone-days whose trips are all non-billable | Omit them: the report publishes a row only where the zone-day has at least one billable trip, keeping today's 7,961 rows. The 36 Q1 2024 zero-billable zone-days stay visible in `agg_trip_zone_daily`, whose grain keeps every in-window zone-day | user answer |
| Metric definitions: which measures the report publishes | The shipped set, unchanged: billable trip count, and fare, tip, surcharge, toll and total revenue summed over billable trips, plus `reporting_region` | request ("No number in our report may change") |
| Coverage: the count of rows carrying a measure | `trip_count` is published beside every revenue measure, so the default is met without a new column | transformation playbook default |
| Reuse: which relation to build on | Build on the published `agg.agg_trip_zone_daily` rather than rebuild from `core.fct_trip` — the request names it as the one source | request |
| Unmatched and null keys | The existing inner join to `dim_zone` is carried over as shipped; in-window the effect is nil (0 of 95,958 billable Q1 trips have a null pickup zone key), so neither keeping nor dropping can change a number | request ("No number in our report may change") + ADR 0015 |
| Extended scope | not applicable — no schedule is requested, so `orchestration` stays out of `kinds:` | transformation playbook |
| ADR 0003: where the billable rule is applied | Amend ADR 0003 in this change: `agg_trip_zone_daily` joins the list of marts that apply the rule and `mart_daily_zone_revenue` leaves it, because the rule now runs once in the aggregate. The billable definition and the rule itself are untouched | user answer |

## Out of scope

- The reporting window (`report_start`, `report_end`) and every other finance, agg and ops mart.
- `agg_trip_zone_daily`'s existing column semantics: `trip_count` and `total_revenue` stay whole-population (R-07).
- The other two finance marts' sources and numbers.
- `docs/setup/` and `docs/review/`.

## Open questions

None: both branches asked before approval were answered — the report omits zone-days with no billable trip (R-05), and ADR 0003 is amended in this change (R-11).

Note, recorded rather than asked: `finance.mart_daily_zone_revenue`'s published description of `trip_count` reads "Trips, billable or not." while the shipped column counts billable trips only (95,958, against 97,184 in-window trips). The description is wrong today; the rebuild corrects the wording, not the value.

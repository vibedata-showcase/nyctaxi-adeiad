# Requirement: RR_Intent2

## Ask

Ravi Menon, who owns the finance reports, asked for the daily zone revenue report Finance reads every morning to be built from the operations figures in `agg` instead of a second build from the trip fact, so that one source produces both. No number in the finance report may change. Finance's usual check, for Q1 2024: the report must total 95,958 trips and 2,629,185.82 revenue, and 4,120 trips and 337,711.05 revenue for JFK Airport.

Consumers: Finance's daily zone revenue report, which reads `finance.mart_daily_zone_revenue`; and Operations' own daily zone figures, which read `agg.agg_trip_zone_daily`. Neither is declared as a dbt exposure in this repo.

## Requirements

- [ ] `R-01` The finance report is built from the operations figures and from no other trip-level relation — accept when `mart_daily_zone_revenue` compiles reading `agg.agg_trip_zone_daily`, and `get_lineage` one hop upstream of the model reaches no other relation than `agg_trip_zone_daily` and `dim_zone` — source: request
- [ ] `R-02` Every number the finance report publishes today is unchanged — accept when, compared cell by cell on `(trip_date, pickup_location_id)` against the Domain's current `finance.mart_daily_zone_revenue`, all 7,961 existing rows are classed `matching` on every one of the eleven published columns, and the only other rows are the all-zero zone-days R-02a admits — source: request
- [ ] `R-02a` A zone-day whose trips are all non-billable appears in the report with 0 trips and 0 revenue rather than being omitted — accept when the report holds 7,997 rows, of which exactly 36 carry `trip_count` 0 and every revenue measure 0, and those 36 are exactly the zone-days in `agg.agg_trip_zone_daily` with no billable trip — source: answer on the population ("Emit them with zero trips and zero revenue — 7,997 rows")
- [ ] `R-03` Finance's acceptance figures hold for Q1 2024 — accept when the rebuilt report totals 95,958 trips and 2,629,185.82 revenue, and totals 4,120 trips and 337,711.05 revenue for the zone `JFK Airport` — source: request
- [ ] `R-04` Operations' published figures are unchanged — accept when each of the 14 existing columns of `agg.agg_trip_zone_daily` compares `EXCEPT ALL`-equal in both directions to the Domain's current table over the reporting window (7,997 rows, 97,184 trips, 2,597,120.92 revenue) — source: request (one source, no number changes), repository
- [ ] `R-05` The billable rule is computed once for this grain — accept when exactly one model in the project computes billable zone-day measures, and the finance model carries no billable filter of its own — source: request, [ADR 0018](../../docs/adr/0018-zone-day-billable-measures-are-computed-once-in-the-aggregate.md)
- [ ] `R-06` Descriptions, contracts, the ADRs and the semantic model match the relations as built — accept when `_finance.yml`, `_agg.yml`, both ODCS contracts, ADR 0018 and the Ossie documents agree with the built columns and their populations (no column described as "billable or not" that carries only billable trips), and `odcs_check`, `ossie_lint` and the semantic structural gates pass — source: repository — `_finance.yml` describes `mart_daily_zone_revenue.trip_count` as "Trips, billable or not." while the model filters to billable trips (95,958 of 97,184 in the window)
- [ ] `R-07` The semantic layer and its tests still answer the same questions — accept when `dbt build --select agg_trip_zone_daily+` and `dbt test --select mart_daily_zone_revenue,agg_trip_zone_daily` pass, including `assert_semantic_content_holds` and `assert_semantic_levels_hold` — source: repository

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of the rebuilt report | One row per pickup zone and trip date (`trip_date` × `pickup_location_id`), unchanged | existing model `finance.mart_daily_zone_revenue` |
| Reuse | Build on the published `agg.agg_trip_zone_daily`, which already carries this grain, rather than a second aggregation from the fact | playbook default (Reuse), repository |
| Edge periods | Not applicable: the loaded window is 2024-01-01 to 2024-03-31 and the reporting window is exactly Q1, so no period is cut short | repository (`fct_trip` min/max pickup date, `dbt_project.yml` vars) |
| Coverage of the new billable measures | Publish the billable trip count beside every billable revenue measure, so a reader sees what the measure covers | playbook default (Coverage) |
| Measure on a zone-day with no billable trip | In the aggregate: `billable_trip_count` 0 with the revenue measures null. In the report: 0 and 0, because its contract makes every published revenue column `not_null` | playbook default (Coverage), answer on the population, `contracts/finance/mart_daily_zone_revenue.odcs.yaml` |
| Unmatched and null keys | Keep every row: the zone join is on the surrogate `pickup_zone_key`, one row per trip, and no in-window trip has a null zone key (0 of 97,184) | repository |
| How the report is built from agg | `agg.agg_trip_zone_daily` gains the billable measures beside its existing unfiltered ones; the finance mart selects and renames them and computes no aggregate. Operations keeps 97,184 trips and 2,597,120.92; Finance keeps 95,958 and 2,629,185.82 | user answer: "Add billable measures to agg; finance mart becomes a projection" |
| Population of the finance report | Zone-days with no billable trip are published with 0 trips and 0 revenue, widening the report from 7,961 to 7,997 rows | user answer: "Emit them with zero trips and zero revenue — 7,997 rows" |
| Where the billable rule is applied | Computed once, in `agg.agg_trip_zone_daily`; [ADR 0003](../../docs/adr/0003-billable-trip-definition-and-where-it-applies.md) is superseded by [ADR 0018](../../docs/adr/0018-zone-day-billable-measures-are-computed-once-in-the-aggregate.md), which keeps ADR 0003's definition and moves its placement for this grain | user answer: "Yes — write a new ADR superseding ADR 0003" |
| Schema of both dbt folders | `agg` and `finance`, unchanged; the user accepted both defaults | user answer at the design stop |

## Out of scope

- `finance.mart_monthly_service_summary` and `finance.mart_revenue_component_bridge`, which keep building from `fct_trip`.
- The existing columns of `agg.agg_trip_zone_daily` and every other `agg`, `core` and `ops` model.
- The reporting window (`report_start`/`report_end`) and the loaded data.
- Retiring either relation, or changing either relation's key or partitioning.
- The ingestion pipelines.

None. Both questions put to the user are answered above; the reconciliation in `docs/verify/2026-11-25-rr-intent2-04937342.md` shows the chosen route reproduces Finance's four figures exactly.

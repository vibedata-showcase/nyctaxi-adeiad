# Requirement: LFQ 3

## Ask

Ravi Menon, who owns the finance reports:

> Finance reads the daily zone revenue report every morning. Operations keeps its own daily figures by zone in the agg schema, so we pay for two builds that should give the same answers. Please build our report from the operations figures, so that there is one source. No number in our report may change. Before we accept a change, we run our usual check: for Q1 2024 the report must show 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips and 337,711.05 revenue for JFK Airport.

The report is `finance.mart_daily_zone_revenue`; the operations figure is `agg.agg_trip_zone_daily`. Finance reads the mart; the Operations team reads the `agg` layer.

**The two builds do not give the same answers today**, so "build from the operations figures" and "no number may change" cannot both hold without changing the operations figure. Measured on the Domain warehouse for 2024-01-01 to 2024-03-31:

| | `finance.mart_daily_zone_revenue` | `agg.agg_trip_zone_daily` |
| --- | --- | --- |
| rows | 7,961 | 7,997 |
| trips | 95,958 | 97,184 |
| total revenue | 2,629,185.82 | 2,597,120.92 |
| JFK Airport (zone 132) trips | 4,120 | 4,261 |
| JFK Airport total revenue | 337,711.05 | 329,766.06 |

The difference is one rule, not two sources. The finance mart applies the billable rule ([ADR 0003](../adr/0003-billable-trip-definition-and-where-it-applies.md)): 1,226 non-billable trips and −32,064.90 of non-billable revenue are excluded, and 36 zone-days whose every trip was non-billable are absent. `agg_trip_zone_daily` counts and sums every trip. Both read `core.fct_trip`: neither reads the fleet-operations source (`ops_raw` appears in no mart), so the saving is one fewer gold zone-day model to build and maintain, not a reconciliation of two systems.

A report rebuilt on billable measures of the operations figure reproduces today's mart exactly: 7,961 rows, and 0 rows differing in any of its 11 columns, recomputed against `core.fct_trip` in a throwaway query.

## Requirements

- [ ] `R-01` `finance.mart_daily_zone_revenue` is built from `agg.agg_trip_zone_daily` rather than aggregating `core.fct_trip` itself, and keeps its 11 published columns, names and types (`trip_date`, `pickup_location_id`, `borough`, `zone_name`, `reporting_region`, `trip_count`, `fare_revenue`, `tip_revenue`, `surcharge_revenue`, `toll_revenue`, `total_revenue`) — accept when the compiled model reads only `agg_trip_zone_daily` and `dim_zone` at zone-day grain, and the enforced contract and properties file list the same columns and types as before this change — source: request
- [ ] `R-02` No number in the report changes — accept when a full outer join of the built mart against production's `finance.mart_daily_zone_revenue` on (`trip_date`, `pickup_location_id`) returns 0 left-only rows, 0 right-only rows, and 0 rows where any of `borough`, `zone_name`, `reporting_region`, `trip_count`, `fare_revenue`, `tip_revenue`, `surcharge_revenue`, `toll_revenue` or `total_revenue` differs at zero tolerance, over all 7,961 rows — source: request
- [ ] `R-03` Q1 2024 totals hold — accept when the built mart sums to exactly 95,958 trips and 2,629,185.82 total revenue over `trip_date` 2024-01-01 to 2024-03-31 — source: request (Finance's acceptance check)
- [ ] `R-04` JFK Airport Q1 2024 holds — accept when the built mart returns exactly 4,120 trips and 337,711.05 total revenue for `pickup_location_id` 132 over the same window — source: request (Finance's acceptance check)
- [ ] `R-05` `agg.agg_trip_zone_daily` gains billable measures sufficient to answer the report — a billable trip count and the billable fare, tip, surcharge, toll and total revenue — published beside its existing unfiltered measures, and no existing column, type or value changes — accept when `trip_count` and `total_revenue` per (`pickup_date`, `pickup_location_id`) equal production's, and the new columns exist with the decided semantics — source: request, [ADR 0003](../adr/0003-billable-trip-definition-and-where-it-applies.md)
- [ ] `R-06` The new billable measures are the billable rule and nothing else — accept when, for every (`pickup_date`, `pickup_location_id`) in the window, the new billable trip count and each new billable revenue equal `core.fct_trip` filtered on `is_billable` inside the report window and grouped the same way, recomputed independently of the model's SQL — source: [ADR 0003](../adr/0003-billable-trip-definition-and-where-it-applies.md)
- [ ] `R-07` There is one zone-day revenue build — accept when `agg_trip_zone_daily` is the only gold relation that aggregates `fct_trip` to zone-day revenue for the report, and no other model recomputes billable zone-day revenue from `fct_trip` — source: request
- [ ] `R-08` What the model publishes stays honest — accept when the `agg_trip_zone_daily` ODCS contract carries the added columns with a moved version and `odcs_check` passes, the Ossie document binding `agg_trip_zone_daily` accounts for the added columns and their metrics, and the `mart_daily_zone_revenue` contract is unchanged — source: repository convention (`repo-map.json` `modules.contracts`, `modules.logical_model`)

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of the report | One row per pickup zone and trip date, as today | existing `mart_daily_zone_revenue` and `agg_trip_zone_daily`, `docs/design/models/finance/mart_daily_zone_revenue.md` |
| Edge periods | Not applicable: the report is daily and no period is cut short — the window's first and last days each carry a full 24 hours (2024-01-01: 888 trips, 2024-03-31: 975 trips) | derived from `core.fct_trip` |
| Population of the report | **Open** — 7,961 rows as today, or all 7,997 with the 36 all-non-billable zone-days at zero | open question 1 |
| New billable measures on an all-non-billable zone-day | **Open** — 0 with the billable trip count beside it, or NULL for the sums | open question 2 |
| Coverage of the billable revenue measures | The billable trip count is published beside the billable revenue, so a reader sees how many trips carry the sum | `../../_shared/playbooks/kinds/transformation.md`, Coverage default |
| Reuse | Build on the published `agg_trip_zone_daily` instead of re-aggregating `fct_trip`; `borough` and `zone_name` come from that model, `reporting_region` from `dim_zone` at its current version | request; derived (see below) |
| Unmatched and null keys | No row is dropped or merged by reusing the aggregation: 0 trips in the window have no `dim_zone` row and 0 fall on a non-current zone version, so `agg_trip_zone_daily`'s join loses nothing and the `dim_zone` lookup for `reporting_region` must filter `is_current_version` to avoid the 7 zones carrying 2 versions | derived from `core.fct_trip`, `core.dim_zone` |
| Billable rule location | Still applied in gold and nowhere upstream: `agg` is gold, and the rule remains one definition on `is_billable` | [ADR 0003](../adr/0003-billable-trip-definition-and-where-it-applies.md) |
| Extended scope | No schedule and no ingestion change; the contract and semantic-layer work stays inside this intent | `repo-map.json` |

## Out of scope

- `mart_monthly_service_summary`, `mart_revenue_component_bridge` and every other gold mart: their numbers and definitions do not change.
- `agg_trip_zone_daily`'s existing measures (`trip_count`, `total_revenue`, `total_miles`, `attributed_driver_count`) and its window columns (`prev_day_trip_count`, `same_day_last_week_trip_count`, `trip_count_7d_avg`, `revenue_28d_rolling`, `revenue_rank_that_day`).
- The billable rule itself, the reporting window (`report_start`/`report_end`) and the reporting-window defaults.
- The fleet-operations source (`ops_raw`) and the `ops` marts: they do not use the billable rule and are not part of the report.
- Review findings in `docs/review/`.

## Open questions

1. **Report population.** Today's mart omits a zone-day whose every trip was non-billable — 36 such zone-days in Q1, each with 0 billable trips and 0 billable revenue, and all 7,997 − 7,961 of the gap. Publishing all 7,997 keeps total trips and total revenue identical but adds 36 rows Finance would newly see, and changes the row count the report already shows. Which population does the report publish? Holds: `R-01`'s row set, `R-02`'s left-only/right-only tolerance, and the `agg_trip_zone_daily` measures work if the answer is to omit them.
2. **Values on an all-non-billable zone-day.** `agg_trip_zone_daily` will carry billable revenue columns; for the 36 zone-days with no billable trip the natural SQL result is NULL, while a computed zero states what actually happened. A `sum(...) filter (...)` yields NULL and a bare aggregate yields 0; ADR 0015 forbids placeholder members but says nothing about an honest zero. Which is published, and does it clear the ADR bar as a standing rule? Holds: `R-05`'s semantics and `R-06`'s comparison.
3. **A design-record conflict to settle at design, not here.** `docs/design/models/finance/mart_daily_zone_revenue.md` `D-01` says the billable rule and the reporting window are applied "here, in gold, and nowhere upstream". Reading a pre-aggregated gold relation moves where the rule is computed, so `D-01` needs amending under `designing`, and the amended wording must stay compatible with ADR 0003's list of marts that apply the rule.
4. **A naming consequence for design.** `agg_trip_zone_daily.total_revenue` already exists and is unfiltered, so the billable total cannot reuse that name; the billable columns need names that cannot be confused with the unfiltered ones (`agg_trip_zone_daypart_dow` uses `billable_trip_count` beside `trip_count`).

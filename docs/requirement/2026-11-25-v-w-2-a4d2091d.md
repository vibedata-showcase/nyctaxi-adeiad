# Requirement: V W 2

## Ask

Ravi Menon, who owns the finance reports, asked: "Finance reads the daily zone revenue report every morning. Operations keeps its own daily figures by zone in the `agg` schema, so we pay for two builds that should give the same answers. Please build our report from the operations figures, so that there is one source. No number in our report may change. Before we accept a change, we run our usual check: for Q1 2024 the report must show 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips and 337,711.05 revenue for JFK Airport."

The consuming report is `finance.mart_daily_zone_revenue`, read each morning by Finance. The operations figures are `agg.agg_trip_zone_daily`.

**The two relations are not two builds of one number.** They hold different populations. Measured on the domain warehouse:

| Q1 2024 | `finance.mart_daily_zone_revenue` | `agg.agg_trip_zone_daily` |
| --- | --- | --- |
| trips | 95,958 | 97,184 |
| revenue | 2,629,185.82 | 2,597,120.92 |
| billable rule (ADR 0003) | applied | not applied ("Trips, billable or not") |

The requested figures are exactly the billable population: `fct_trip` holds 97,184 trips in the window, 95,958 of them billable, and the 1,226 non-billable trips carry −32,064.90 of total amount, which is precisely the gap between the two relations. `agg_trip_zone_daily` aggregates `total_amount` over all trips, so its aggregate cannot be split back apart: 36 zone-days are entirely non-billable and 962 zone-days mix billable with non-billable trips. No query over `agg.agg_trip_zone_daily` as it stands can produce 95,958 / 2,629,185.82. It also publishes only `total_revenue`, not the `fare_revenue`, `tip_revenue`, `surcharge_revenue` and `toll_revenue` columns the finance report carries.

So "build the report from the operations figures" and "no number may change" both hold only if the operations relation carries the billable measures too. That is what this Requirement asks for, as an additive change.

## Requirements

- [ ] `R-01` The daily zone revenue report is built from the operations figures, so the daily-zone aggregation is computed once — accept when the compiled graph shows `mart_daily_zone_revenue` depends on `agg_trip_zone_daily` and reads no trip-grain relation directly — source: request
- [ ] `R-02` No number in the report changes — accept when the rebuilt `mart_daily_zone_revenue` has 7,961 rows, 0 unmatched `(trip_date, pickup_location_id)` pairs and 0 differing values against the pre-change build across all six measures, and recomputes Q1 2024 as 95,958 trips / 2,629,185.82 revenue and JFK Airport as 4,120 trips / 337,711.05 revenue — source: request acceptance figures
- [ ] `R-03` The operations relation's published promise is not weakened: its 14 existing columns keep their names, types and values — accept when `agg_trip_zone_daily` still has 7,997 rows with identical values in `trip_count`, `total_revenue` and its other 12 existing columns against the pre-change build — source: request ("no number may change") and its active contract
- [ ] `R-04` The operations relation carries the billable population and the revenue components the report reads — accept when `agg_trip_zone_daily` publishes `billable_trip_count`, `billable_revenue`, `fare_revenue`, `tip_revenue`, `surcharge_revenue` and `toll_revenue`, and summing `billable_trip_count` over Q1 2024 gives 95,958 — source: request; ADR 0003
- [ ] `R-05` A zone-day with no billable trip stays absent from the report rather than appearing as a zero row — accept when the rebuilt report has no row with `billable_trip_count = 0` and the 36 all-non-billable zone-days are absent from it — source: request ("no number may change")
- [ ] `R-06` The billable rule keeps one definition and the report still states that it applies it — accept when the rebuilt report's output is exactly the billable population (R-02) and its description and `trip_count` description state that it counts billable trips — source: ADR 0003; this intent's finding F-01
- [ ] `R-07` The changed boundary relations' contracts, semantic model and ontology agree with what was built — accept when `agg_trip_zone_daily`'s contract names the six new columns with their types, its Ossie logical source binds them with a declared metric each, and the contract, semantic-model and ontology validation gates all pass — source: repository convention (`repo-map.json`, `contracts/`, `logical-model/`)
- [ ] `R-08` The finance report's published shape does not change — accept when `mart_daily_zone_revenue`'s contract still names the same 11 columns with the same types — source: request ("no number may change"); no consumer asked for a shape change

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of the report and of the operations relation | One row per pickup zone and trip date, unchanged | request ("daily ... by zone"); existing `mart_daily_zone_revenue` and `agg_trip_zone_daily` |
| Edge periods | Not applicable: neither window edge is cut short. 2024-01-01 and 2024-03-31 each carry a full 24 hours of pickups (888 and 975 trips, first pickup 00:05:25 and 00:00:22, last 23:59:25 and 23:56:17) | query against `fct_trip` |
| Population the report publishes | Billable trips only, unchanged. ADR 0003: "Gold marts that report revenue or flows apply it, inside the reporting window: `mart_daily_zone_revenue`, `mart_monthly_service_summary`, `mart_revenue_component_bridge` and `agg_od_flow_matrix`." | ADR 0003, quoted; request acceptance figures |
| Population of the operations relation's existing columns | All trips, unchanged, and the billable measures sit beside them rather than replacing them | request ("No number in our report may change"); `agg_trip_zone_daily`'s active contract; ADR 0003 ("Marts that profile quality or banding report billable and non-billable counts side by side instead of filtering") |
| Whether a zone-day with no qualifying row is emitted as zero or omitted | Omitted, as today: 36 zone-days in the window have no billable trip and appear in no report row | request ("No number in our report may change"); query against `fct_trip` and both relations |
| Coverage of the six measures | Not applicable: every measure is present on every billable row — 0 nulls in `fare_amount`, `tip_amount`, `total_surcharges`, `tolls_amount` and `total_amount` across all 95,958 billable trips, so no count needs to stand beside them | query against `fct_trip` |
| Reuse | Build on `agg_trip_zone_daily`, which already serves the requested grain exactly, and extend it with the billable measures; no second daily-zone aggregation is introduced | request ("build our report from the operations figures"); playbook Reuse default |
| Unmatched and null keys | Keep every row. No trip in the window has a null pickup zone and no `(date, zone)` pair fails to match between the two relations, so the rebuild may drop nothing. The join from the operations relation to `dim_zone` must resolve to the current zone version: `dim_zone` holds 7 natural keys in more than one version, and joining on the natural key alone fans 223 zone-days out to multiple rows | query against `fct_trip`, `dim_zone` and both relations |
| Extended scope | Not a question. No schedule is added, so `kinds:` stays `[transformation]`; the contract, Ossie and ontology deliverables stay inside it because all are built from the boundary dbt model | playbook Extended scope |

Pending for design, not asked here: whether the operations relation also gains `reporting_region` or the report keeps joining `dim_zone` for its three descriptive attributes; the materialisation; and the metric names the four component revenues declare in the Ossie document, since no metric exists for them today.

## Findings

- `F-01` `mart_daily_zone_revenue`'s `trip_count` description reads "Trips, billable or not", but the model filters `f.is_billable`, so the column is the billable count (0 rows differ from the billable count over all 7,961 rows). The description contradicts the data and is corrected under `R-06`.
- `F-02` The two relations the request calls duplicate builds measure different populations, so the premise "two builds that should give the same answers" does not hold and swapping the source alone would have changed every figure. Recorded here rather than silently reconciled.

## Out of scope

- `agg_trip_zone_daily`'s 14 existing columns: no name, type or value changes.
- Every published model the request did not name: `mart_monthly_service_summary`, `mart_revenue_component_bridge`, `agg_od_flow_matrix`, the other `agg` models and every `ops` mart stay untouched.
- `fct_trip`, `dim_zone` and the rest of the staging and intermediate layers; the reporting window variables in `dbt_project.yml`.
- `mart_daily_zone_revenue`'s published columns: none added, removed or retyped.
- Any schedule or orchestration item.

## Open questions

None. The population branch that decides row counts and values is settled by the request's own acceptance figures together with ADR 0003, and every other branch is settled by the repository or the playbook default above.

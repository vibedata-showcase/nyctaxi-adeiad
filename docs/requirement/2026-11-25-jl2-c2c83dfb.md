# Requirement: jl2

## Ask

Ravi Menon, who owns the finance reports, asked:

> Finance reads the daily zone revenue report every morning. Operations keeps its
> own daily figures by zone in the agg schema, so we pay for two builds that
> should give the same answers. Please build our report from the operations
> figures, so that there is one source. No number in our report may change.
> Before we accept a change, we run our usual check: for Q1 2024 the report must
> show 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips and
> 337,711.05 revenue for JFK Airport.

Consumer: the finance team's daily zone revenue report (`finance.mart_daily_zone_revenue`).

**The premise needs correcting, and the correction drives the design.** The two
builds do not give the same answers today, and could not:

| Relation | Rows | Trips | Revenue |
| --- | --- | --- | --- |
| `finance.mart_daily_zone_revenue` | 7,961 | 95,958 | 2,629,185.82 |
| `agg.agg_trip_zone_daily` | 7,997 | 97,184 | 2,597,120.92 |

The gap is not an error on either side. The finance report applies the billable
rule (ADR 0003) and so counts only positive-total trips; the agg counts every
in-window trip, refunds included. They also share only 5 of the report's 11
columns: the agg carries no fare/tip/surcharge/toll split and no
`reporting_region`.

So "one source, no number changes" is satisfied by extending the shared relation
to carry what the report needs, not by pointing the report at the relation as it
stands today. The user chose to add the billable measures beside the existing
all-trips ones, so that Operations' published figures do not move either
(business decision 3).

## Requirements

- [ ] `R-01` The daily zone revenue report is built from `agg.agg_trip_zone_daily` as its only upstream relation; `mart_daily_zone_revenue.sql` holds no `ref('fct_trip')` and no `ref('dim_zone')` — accept when the compiled model's dependency list contains `agg_trip_zone_daily` and neither of those two, read from `target/manifest.json` — source: request
- [ ] `R-02` `agg.agg_trip_zone_daily` additionally publishes the billable measures the report reads: billable trip count, billable fare revenue, billable tip revenue, billable surcharge revenue, billable toll revenue and billable total revenue — accept when the built relation exposes each column and, over the reporting window, `sum(billable trip count)` = 95,958 and `sum(billable total revenue)` = 2,629,185.82 — source: answer (additive), evidence below
- [ ] `R-03` `agg.agg_trip_zone_daily` publishes `reporting_region`, matching `dim_zone.reporting_region` for every zone — accept when the report's `reporting_region` equals the merge-base report's for every row — source: request ("one source"; the report reads this column), repository (`dim_zone.reporting_region`)
- [ ] `R-04` The report's published shape is unchanged: the same 11 columns with the same names and types, one row per `trip_date` × `pickup_location_id`, `trip_date` typed DATE — accept when `dbt test --select mart_daily_zone_revenue` passes the enforced contract and a grain-uniqueness check finds no duplicate `(trip_date, pickup_location_id)` — source: request ("no number in our report may change"), repository
- [ ] `R-05` Every one of the 7,961 report rows is value-identical to the merge-base report: `trip_count`, `fare_revenue`, `tip_revenue`, `surcharge_revenue`, `toll_revenue`, `total_revenue`, `borough`, `zone_name`, `reporting_region` — accept when a row-level full outer join against the merge-base relation at the frozen tolerance returns zero mismatched and zero unmatched rows in either direction — source: request ("no number in our report may change")
- [ ] `R-06` Q1 2024 acceptance check: the report totals 95,958 trips and 2,629,185.82 revenue, and JFK Airport totals 4,120 trips and 337,711.05 revenue — accept when those four figures come back exactly (revenue to the cent) from a query over the built relation — source: request (Ravi Menon), confirmed against the merge-base report
- [ ] `R-07` Operations' figures do not move: `agg.agg_trip_zone_daily`'s existing `trip_count` and `total_revenue` keep their all-trips meaning and values — accept when `sum(trip_count)` = 97,184 and `sum(total_revenue)` = 2,597,120.92 over the reporting window, and the row count stays 7,997 — source: answer (additive)
- [ ] `R-08` A zone-day with no billable trip stays absent from the report, as today: the 36 zone-days whose 37 in-window trips were all refunds appear neither as a row nor as a zero row — accept when the report has 7,961 rows and none of those 36 `(trip_date, pickup_location_id)` pairs is present — source: answer (omit)
- [ ] `R-09` Every relation this intent publishes carries a contract and a semantic-model binding that agree with the built relation: the agg contract names the new columns, and the `agg_trip_zone_daily` logical-source binding declares the billable measures it now supplies — accept when `odcs.py check` and the `validating-data-contract` and `validating-semantic-model` gates pass — source: repository (`contracts/`, `logical-model/`, ADR-0225 boundary)
- [ ] `R-10` Descriptions state the population a column actually carries: the report's `trip_count` is documented as the billable trip count, not "trips, billable or not", and the agg's `trip_count` is documented as all in-window trips — accept when each description is read against the built relation and agrees with it — source: repository finding (see below)

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of the shared relation and of the report | One row per pickup date × pickup zone, unchanged: `agg_trip_zone_daily` keeps `(pickup_date, pickup_location_id)` and the report keeps `(trip_date, pickup_location_id)`; the period boundary is the existing reporting window, 2024-01-01 inclusive to 2024-04-01 exclusive | request ("daily zone revenue report", "daily figures by zone"); existing models |
| Edge periods | `not applicable` — the window covers 2024-01-01 to 2024-03-31 in full, three whole months, so no period is cut short by the data window; the acceptance check is a whole-quarter total | repository (`dbt_project.yml` vars; `min`/`max` of `trip_date` are 2024-01-01 and 2024-03-31) |
| Population of the report's measures | Billable trips only (positive total), inside the reporting window — unchanged | request ("no number may change"); ADR 0003, which names `mart_daily_zone_revenue` among the marts that apply the rule |
| Population of the shared relation | Keeps all in-window trips in `trip_count`/`total_revenue` and gains billable measures beside them, rather than redefining the existing columns as billable | user answer (additive) — asked because it changes Operations' published values |
| Row emitted for a zone-day with no billable trip | Omitted, as today; no zero row | user answer (omit) — asked because it changes the report's row count |
| NULLs in the billable revenue aggregates | The report's five revenue measures are sums over trips where the measure is always present; on the 95,958 billable trips none of `total_amount`, `fare_amount`, `tip_amount`, `total_surcharges`, `tolls_amount` is null, so `sum` and `sum ... filter` give the same value and no coalesce is introduced | repository (query over `fct_trip`: 0 nulls on every measure) |
| Coverage | The billable trip count is published beside the billable revenue measures; that count is the coverage statement, and the report's `trip_count` carries it | playbook default (publish the count) |
| Reuse | Build on the published `agg.agg_trip_zone_daily` rather than rebuilding the rollup or restructuring it; the report becomes its consumer | request ("build our report from the operations figures"); playbook default |
| Unmatched and null keys | Kept exactly as today: the report joins the zone on an inner join, and no in-window trip has a null pickup zone (0 rows), so the join drops nothing and no row is added or relabelled | repository (query over `fct_trip`: 0 null `pickup_zone_key` in window) |
| Extended scope | Not a question: no schedule is requested, so `orchestration` is not added to `kinds:` | playbook |

## Out of scope

- `mart_monthly_service_summary` and `mart_revenue_component_bridge`: they apply ADR 0003 too, but the request names only the daily zone report. They keep reading `fct_trip`.
- `agg_trip_zone_daypart_dow` and the other `agg` marts: untouched. In particular the daypart cube keeps its own all-trips `trip_count` with `billable_trip_count` beside it; it is not folded into this change.
- Redefining or removing any existing published agg column, or changing the reporting window.
- Any change to the ingestion, the TLC source data, or the trip fact itself.
- A new mart, or a new column on the report: the report's published shape stays exactly as it is.

## Open questions

**A docs defect found while reading, folded into `R-10`, not asked:** `trip_count` on both relations is described in `_finance.yml` as "Trips, billable or not", but the report filters on `is_billable`, so it is the billable count. The logical model already records this correctly ("the mart applies `f.is_billable`, so its `trip_count` is the billable count"). This is a description to correct in the change that touches the relation, not a business decision.

None open.

# Requirement: Build the daily zone revenue report from the operations figures

## Ask

Ravi Menon, who owns the finance reports: finance reads the daily zone revenue report every morning, and operations keeps its own daily figures by zone in the `agg` schema, so the Domain pays for two builds that should give the same answers. Build the report from the operations figures so there is one source, and let no number in the report change.

Acceptance, run by finance before accepting a change: for Q1 2024 the report must show 95,958 trips and 2,629,185.82 revenue in total, and 4,120 trips and 337,711.05 revenue for JFK Airport.

Consumers: the finance team reading `finance.mart_daily_zone_revenue`; the canonical semantic model, which binds it as logical source `LTS7_daily_zone_revenue`; and the Domain's singular semantic tests.

**What the two builds actually measure** (read from the Domain warehouse on 2026-11-25, reporting window 2024-01-01 to 2024-04-01):

| Q1 2024 | `finance.mart_daily_zone_revenue` | `agg.agg_trip_zone_daily` |
| --- | --- | --- |
| rows | 7,961 | 7,997 |
| trips | 95,958 | 97,184 |
| revenue | 2,629,185.82 | 2,597,120.92 |
| JFK Airport trips / revenue | 4,120 / 337,711.05 | 4,261 / 329,766.06 |

They are not two builds of one answer. `agg_trip_zone_daily` counts and sums every trip in the window; the finance report counts and sums billable trips only, as ADR 0003 requires of it. The `fct_trip` difference is exactly the 1,226 non-billable trips worth −32,064.90: 95,958 + 1,226 = 97,184 and 2,629,185.82 − 32,064.90 = 2,597,120.92. `agg_trip_zone_daily` also lacks `reporting_region` and the fare, tip, surcharge and toll revenue columns the report publishes, and 36 zone-days in the window have no billable trip, so the report's row set is not a filter over the ops rows either.

The single source is therefore reached by **extending `agg_trip_zone_daily` with the billable figures and having the report select from it** (the answer recorded below), not by pointing the report at the ops table as it stands.

## Requirements

- [ ] `R-01` `finance.mart_daily_zone_revenue` is built from `agg.agg_trip_zone_daily` and reads no other relation — accept when the compiled model references `agg_trip_zone_daily` alone, with no `ref` to `fct_trip` or `dim_zone`, and `dbt build --select mart_daily_zone_revenue` passes — source: request ("build our report from the operations figures, so that there is one source")
- [ ] `R-02` `agg.agg_trip_zone_daily` carries the billable measures the report needs at its existing grain: the billable trip count, billable fare, tip, surcharge, toll and total revenue, and `reporting_region` — accept when the built relation contains one column per measure with a declared type, its enforced contract names them, and a recomputation of each from `fct_trip` replicates the built values at cent precision — source: answer to the `one source` question (extend `agg_trip_zone_daily`)
- [ ] `R-03` Every existing column of `agg.agg_trip_zone_daily` keeps its population and its values: `trip_count` and `total_revenue` stay all-trips measures over the same 7,997 rows — accept when the relation has 7,997 rows over the same (pickup date, pickup location) keys as today and `trip_count` and `total_revenue` recompute from `fct_trip` with zero differing rows — source: answer to the `one source` question; ADR 0003 (the billable rule applies to marts that report revenue, not to a demand aggregate)
- [ ] `R-04` No number in the report changes: Q1 2024 totals of 95,958 trips and 2,629,185.82 revenue, and 4,120 trips and 337,711.05 revenue for JFK Airport — accept when both are read from the rebuilt `finance.mart_daily_zone_revenue` — source: request (finance's acceptance check)
- [ ] `R-05` No row of the report changes: same 7,961 rows on the same (trip date, pickup location) keys, and every published column equal to the pre-change table — accept when a full-column comparison of the rebuilt table against the pre-change table, money compared at cent precision, reports zero differing rows and zero rows only on either side — source: request ("no number in our report may change")
- [ ] `R-06` A zone-day with no billable trip stays in `agg.agg_trip_zone_daily` with a zero billable count and zero billable revenue, and is absent from the report — accept when the 36 such zone-days in the window are present in the ops table with zero billable values and the report has 7,997 − 36 = 7,961 rows — source: playbook default (keep every row) for the ops table; request (`no number may change`) for the report
- [ ] `R-07` The report's documentation states what it publishes: `trip_count` is the billable trip count, and the model description (and the design record) say the billable aggregation is done in `agg_trip_zone_daily` and the report selects it — accept when no description on `mart_daily_zone_revenue` claims a non-billable count or a filter applied in the mart, and the docs-match-data check passes — source: `logical-model/nyc_taxi_analytics.ossie.yaml` LTS7 note ("the mart applies f.is_billable, so its trip_count is the billable count"); today's `transformation/models/marts/finance/_finance.yml` description "Trips, billable or not" contradicts that

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain of `mart_daily_zone_revenue` | One row per pickup zone and trip date | existing model; request (`no number may change`) |
| Grain of `agg_trip_zone_daily` after the change | Unchanged: one row per pickup date and pickup location | existing model; `tests` on the relation |
| Edge periods | not applicable: the report's period is a day, and the data covers all 91 days of Q1 2024 (min 2024-01-01, max 2024-03-31), so no period is cut short | `fct_trip` date span |
| Population of the report | Billable trips inside the reporting window: "A trip is **billable** when its total amount is positive… Gold marts that report revenue or flows apply it, inside the reporting window" | ADR 0003, quoted |
| Population of the new ops columns | Billable trips; the existing all-trips columns are left alone | answer to the `one source` question (`extend_agg`) |
| Where the billable rule is applied | Applied once, in `agg.agg_trip_zone_daily`, and the report selects it. This amends `D-01` of `docs/design/models/finance/mart_daily_zone_revenue.md`, whose wording is "Apply the billable rule and the reporting window here, in gold, and nowhere upstream": the rule is still applied in gold, as ADR 0003 requires, but no longer in this mart. The rule's own statement and its list of marts are unchanged, so ADR 0003 is not reversed | ADR 0003, quoted; `D-01` conflict resolved by the user's answer to the `one source` question |
| NULL handling in the new billable measures | `SUM` skips nulls exactly as the report does today; billable amounts are never null because a billable trip has a positive total | derived: the recomputation that reproduces today's numbers exactly |
| Coverage | The billable trip count is published beside the billable revenue measures | playbook default |
| Reuse | Build on the published `agg_trip_zone_daily` rather than a new aggregate | playbook default; answer to the `one source` question |
| Unmatched and null keys | Keep every row: the ops table keeps its zero-billable zone-days; the report keeps the zone-days that have a billable trip. No window trip has a null or unmatched pickup zone (0 rows) | playbook default (keep every row); request (`no number may change`) |
| Extended scope | not applicable: no schedule is requested, so no `orchestration` kind | request |

## Out of scope

- `finance.mart_monthly_service_summary` and `finance.mart_revenue_component_bridge`, and every `ops` mart. Their descriptions repeat the same "Trips, billable or not" wording for a billable count; that defect is recorded here as a finding and is not fixed by this intent.
- Any change to `fct_trip`, `dim_zone`, `int_trip_quality_flags` or the reporting window.
- Any new published column on, or any population change to, `mart_daily_zone_revenue`: its eleven columns and its 7,961 rows stay as they are.
- Demand-grain measures of `agg_trip_zone_daily` (`total_miles`, `attributed_driver_count`, the lag/rolling/rank window columns) and its use by the quality work: untouched.

## Open questions

None. Columns added to `agg_trip_zone_daily` are a published-shape change, so its breaking-contract stop runs at design; naming the new columns and whether the semantic model routes the billable metrics through the ops source are design decisions, recorded pending for design.

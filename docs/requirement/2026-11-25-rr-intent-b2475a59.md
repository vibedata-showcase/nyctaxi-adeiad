# Requirement: RR_Intent

## Ask

Leila Haddad, Mobility Planning Lead, asked: "The city asked how much of our traffic crosses borough lines. For each month of Q1 2024, I need the trips and the revenue from each borough to each borough, and the share of trips that leave the borough they started in."

The result is a boundary table that a city-facing report and ad-hoc analysis read: one row per month, origin borough and destination borough, with the trips and revenue of that pair and the share of the origin borough's trips that leave it.

## Requirements

- [ ] `R-01` A new boundary aggregate publishes trips and revenue for every (month, origin borough, destination borough) pair carrying at least one billable trip, for the three months of Q1 2024 — accept when the relation returns 40, 40 and 42 rows for 2024-01, 2024-02 and 2024-03 — source: request; user answers on the floor and empty pairs
- [ ] `R-02` The grain is one row per (month, origin borough, destination borough) — accept when a uniqueness test over the three key columns returns no rows — source: request
- [ ] `R-03` `trip_count` is the billable trips of the pair, counted in the pickup month — accept when its monthly totals equal 29,985, 30,017 and 35,956 trips, summing to 95,958 for Q1 — source: request; ADR 0003; `fct_trip` in the domain warehouse
- [ ] `R-04` `total_revenue` is the sum of `total_amount` over those same trips — accept when its monthly totals equal 816,057.76, 813,885.68 and 999,242.38, summing to 2,629,185.82 for Q1 — source: existing revenue marts (`agg_od_flow_matrix`, `mart_daily_zone_revenue`); `fct_trip`
- [ ] `R-05` `cross_borough_share` is, per origin borough and month, the trips ending in a different borough over all the borough's trips that month — accept when an independent recomputation from `fct_trip` reproduces every row, and 2024-01 Manhattan reads 6.01% (1,598 of 26,593) — source: user answer; ADR 0018
- [ ] `R-06` Every borough group the zone master names is reported, the unresolved groups and EWR included, and no trip is dropped for an unresolved zone — accept when all eight origins appear in each month and Q1 trips total 95,958, of which 360 have an unresolved origin — source: user answer; ADR 0012; ADR 0018
- [ ] `R-07` No trip floor narrows the table — accept when a pair carrying a single trip is published (the smallest January pair carries 1) and the Q1 trip total equals the window's billable trip count of 95,958 — source: user answer; ADR 0018
- [ ] `R-08` Rows are confined to the reporting window's Q1 2024 months — accept when exactly three distinct months appear and no pickup date outside 2024-01-01 (inclusive) to 2024-04-01 (exclusive) contributes — source: request; `dbt_project.yml` report window
- [ ] `R-09` The new boundary relation carries its data contract, column descriptions and tests, as the boundary layer requires — accept when `odcs.py check` passes for the relation and every column has a description in the properties file — source: `repo-map.json` (boundary role; the `contracts` module puts every gold relation under contract)

## Business decisions

| Decision | Value | Source |
| --- | --- | --- |
| Grain | One row per (month, origin borough, destination borough) | request |
| Period and its boundary | The calendar month of the trip's pickup (`date_trunc('month', pickup_datetime)`), inside the reporting window 2024-01-01 to 2024-04-01, which is exactly Q1 2024 | request; `dbt_project.yml` vars; `in_report_window` macro |
| Edge periods | not applicable, because no Q1 month is cut short: the loaded data covers 2024-01-01 00:05 to 2024-03-31 23:56 with all 31, 29 and 31 days present in the domain warehouse | domain query over `core.fct_trip` |
| Trips counted | Billable trips only, per ADR 0003: "A trip is **billable** when its total amount is positive… Gold marts that report revenue or flows apply it, inside the reporting window" | ADR 0003; user answer on the population |
| Trip floor | None: a borough pair is published as soon as it carries one billable trip; ADR 0017's 25-trip floor stays scoped to the zone-pair matrix | user answer; ADR 0018 |
| Revenue | Sum of `total_amount` over the pair's billable trips, named `total_revenue` | existing `agg_od_flow_matrix` and `mart_daily_zone_revenue` |
| Cross-borough share | Per origin borough and month: its trips ending in a different borough ÷ all its trips that month; repeated on each of its rows | user answer; ADR 0018; `CONTEXT.md` |
| Borough scope | All eight borough groups `dim_zone` names: Bronx, Brooklyn, Manhattan, Queens, Staten Island, EWR, Unknown, N/A | user answer; ADR 0012; `dim_zone.borough_name` |
| Empty pairs | A borough pair with no billable trips in a month is omitted, not published as zero | user answer |
| NULLs in the measures | None to handle: among Q1 billable trips, 0 have a null or non-positive `total_amount` and 0 have a null pickup or dropoff zone key | domain query over `core.fct_trip` |
| Coverage of revenue | Not a coverage question beyond what the request asks: the trip count that carries the revenue is published beside it as `trip_count`, and no row lacks the measure | request; domain query over `core.fct_trip` |
| Reuse | A new aggregate built on `fct_trip` with `dim_zone` joined twice; `agg_od_flow_matrix` publishes a finer grain but a floored population, so rolling up its rows would inherit the floor and change both the trips and the share | `agg_od_flow_matrix.sql`; ADR 0017; ADR 0018 |
| Unmatched and null keys | Keep every row: the zone join is as-of on the trip's pickup date, and an unresolved borough is a real dimension row (ADR 0012), not an unmatched lookup | ADR 0012; ADR 0015 |
| Same-borough pairs | `origin_borough = dest_borough` is kept as a row, with its trips and revenue, and contributes nothing to the cross-borough share | user answer; ADR 0018 |
| Model and column naming, materialisation, layer file layout | Pending, recorded for design | not asked at intent |

## Out of scope

- `agg_od_flow_matrix`, its 25-trip floor, its contract and its logical source: unchanged, and its population stays narrower than this table.
- `fct_trip`, `dim_zone` and every other published model the request did not name: unchanged.
- No schedule, job or ingestion change: this intent adds no orchestration and no source.
- No change to the reporting window, the billable rule or the unresolved-zone policy.
- Metrics already published in the semantic model keep their definitions; only a new relation and its own mapping arrive.

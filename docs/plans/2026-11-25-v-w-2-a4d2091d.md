# Plan: V W 2

**Goal:** Build the Finance daily zone revenue report from the operations daily-zone figures, so the daily zone aggregation is computed once, without changing any published number.

**Requirement:** `docs/requirement/2026-11-25-v-w-2-a4d2091d.md`

**Constraints:**
- The daily zone aggregation is built once, in `agg_trip_zone_daily`, carrying both populations side by side (ADR 0018).
- The billable rule is `f.is_billable` and applies to the report, inside the reporting window (ADR 0003).
- `agg_trip_zone_daily`'s 14 existing columns keep their names, types and values; 7,997 rows before and after (R-03).
- `mart_daily_zone_revenue` publishes the same 11 columns with the same names and types (R-08).
- Money is compared at the cent (`round(x, 2)`); DuckDB float aggregation is not bit-reproducible (dbt-testing, "Comparing values").
- Every output expression on a contracted relation is cast to its declared `data_type` (duckdb_local dialect card, `## Type fidelity`).
- On a contracted relation the contract is authored first and `generate` writes `data_type`, `data_tests` and `description`; a hand edit there is lost (data-contract skill, workarounds).
- The Ossie document, its regenerated tests and the ontology mapping move in the same commit as the dbt model (canonical-artifacts reference).
- Schemas unchanged: `marts/agg` → `agg`, `marts/finance` → `finance`.

**Baseline build_sha:** not applicable — the `duckdb_local` dbt card's `## Defer` says no production manifest is published, so `/data/cache` is never read.

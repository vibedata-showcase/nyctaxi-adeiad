## Findings

- **Wording agrees with the data.** Every claim this intent wrote was recomputed. The contract's grain text, `_agg.yml`'s model description and the design record all say "no floor", "omitted rather than zero", "unresolved and out-of-state count as crossings" and "rows sum to the origin-month total"; the queries above return 122 rows with no floor, 0 zero rows, 42 unresolved/out-of-state destination rows, and `rows_vs_denominator_diff = 0`. ADR 0018 and ADR 0019 state no figures, so nothing in them can go stale; `CONTEXT.md`'s two entries likewise state rules only.
- **`bindings/unproven` on other sources is a limit of this verification, not a defect.** 14 warnings name marts whose SQL the partial `dbt compile --select agg_borough_flow_monthly` left out of the manifest. None names `LTS10_borough_flow_month`; a full `dbt compile` is what would clear the rest, and it does not bear on this intent's rows.
- **Ontology `glossary` reports `Cross-borough share` as a term without a concept.** That is correct: the term names a measure, not a thing with identity, so the ontology's own rule 1 keeps it prose. No ontology change was due.
- **`odcs.py check --relations` fails on six audit relations outside this intent.** They are `bronze`, `ops_raw` and `mdm_raw` `audit_runs` / `audit_table_loads`, loaded by dlt and so absent from dbt's catalog. Pre-existing and outside the impacted set, so it is a finding and does not block.
- **One naming correction during execution.** The star's `trip_count` metric counts all trips, so `generate` wrote "Trips, billable or not." onto a billable-only column. The counts were renamed for their population (`billable_trip_count`, `billable_revenue`, `cross_borough_billable_trip_count`, `origin_billable_trip_count`) in the model, the contract, the properties file, the unit tests and the singular test, and the description is now true of the column.

## Discovery

- `core.fct_trip` covers Q1 2024 exactly: first pickup 2024-01-01T00:05:25, last 2024-03-31T23:56:17, 97,184 trips, 91 distinct pickup dates — `select min(pickup_datetime) as first_trip, max(pickup_datetime) as last_trip, count(*) as trips from core.fct_trip` and `select min(pickup_date) as d0, max(pickup_date) as d1, count(distinct pickup_date) as days from core.fct_trip`
- Every day of the window carries trips, so no month is cut short: 91 calendar days 2024-01-01…2024-03-31, 91 days with trips, minimum 671 trips on any day — `with b as (select distinct borough_name from core.dim_zone), d as (select unnest(generate_series(date '2024-01-01', date '2024-03-31', interval 1 day))::date as cal_date), t as (select pickup_date, count(*) c from core.fct_trip where pickup_datetime >= date '2024-01-01' and pickup_datetime < date '2024-04-01' group by 1) select (select count(*) from b) as boroughs, (select string_agg(borough_name, ' | ' order by borough_name) from b) as borough_list, (select count(*) from d) as calendar_days, (select count(*) from t) as days_with_trips, (select min(c) from t) as min_trips_per_day`
- Both zone keys resolve on every in-window trip: 0 null `pickup_zone_key`, 0 null `dropoff_zone_key`, and no left join to `core.dim_zone` drops a row — `select count(*) as trips, count(*) filter (where pickup_zone_key is null) as null_pickup_zone, count(*) filter (where dropoff_zone_key is null) as null_dropoff_zone, count(*) filter (where is_billable) as billable from core.fct_trip where pickup_datetime >= date '2024-01-01' and pickup_datetime < date '2024-04-01'` — 97,184 trips, 0 / 0 null keys, 95,958 billable.
- `total_amount` needs no null handling on this population: 0 null totals, 0 null totals among billable trips, 0 zero totals among billable trips — `select count(*) filter (where total_amount is null) as null_total, count(*) filter (where is_billable and total_amount is null) as null_total_billable, count(*) filter (where is_billable and total_amount = 0) as zero_billable from core.fct_trip where pickup_datetime >= date '2024-01-01' and pickup_datetime < date '2024-04-01'`
- Eight borough groups exist in `core.dim_zone`, five of them in NYC: Bronx, Brooklyn, EWR (`is_nyc` false, reporting region `Out of State`), Manhattan, N/A (`is_nyc` false, `Unresolved`), Queens, Staten Island, Unknown (`is_nyc` false, `Unresolved`) — `select borough_name, borough_code, reporting_region, is_nyc, is_core_market, count(*) as zones from core.dim_zone where is_current_version group by 1,2,3,4,5 order by 1`
- The observed population is 122 (month, origin, destination) groups of billable trips in Q1, all 48 origin-destination pairs across the three months summed, none of them carrying zero trips; the dense cross product would be 8 × 8 × 3 = 192 — `select o.borough_name as origin_borough, d.borough_name as dest_borough, count(*) as trips, sum(f.total_amount) as revenue from core.fct_trip f left join core.dim_zone o on f.pickup_zone_key = o.zone_key left join core.dim_zone d on f.dropoff_zone_key = d.zone_key where f.pickup_datetime >= date '2024-01-01' and f.pickup_datetime < date '2024-04-01' and f.is_billable group by 1,2 order by 1,2` (48 rows) and `select m, count(*) from (…) group by 1` — 40, 40 and 42 observed pairs in January, February and March.
- A 25-trip floor would drop 66 of the 122 cells and distort the share badly at this grain: Jan Bronx 59.26% → 49.43%, and the denominator moves from 95,958 trips to 95,705 — `with p as (select date_trunc('month', f.pickup_datetime)::date as m, o.borough_name as ob, d.borough_name as db, count(*) as trips from core.fct_trip f join core.dim_zone o on f.pickup_zone_key = o.zone_key join core.dim_zone d on f.dropoff_zone_key = d.zone_key where f.pickup_datetime >= date '2024-01-01' and f.pickup_datetime < date '2024-04-01' and f.is_billable group by 1,2,3) select count(*) as rows_observed, count(*) filter (where trips >= 25) as rows_over_25, count(*) filter (where trips < 25) as rows_under_25, count(*) filter (where trips < 5) as rows_under_5, sum(trips) as trips_kept_if_floor, min(trips) as min_trips from p` — 122 / 56 / 66 / 51 / 95,705 / 1.
- Counting unresolved and out-of-state destinations as crossings changes the share materially, which is why it was a question rather than a default: Manhattan January 6.01% against 5.53%, Queens 71.54% against 68.19% — `with base as (select date_trunc('month', f.pickup_datetime)::date as m, o.borough_name ob, d.borough_name db, count(*) trips from core.fct_trip f join core.dim_zone o on f.pickup_zone_key=o.zone_key join core.dim_zone d on f.dropoff_zone_key=d.zone_key where f.pickup_datetime>=date '2024-01-01' and f.pickup_datetime<date '2024-04-01' and f.is_billable group by 1,2,3) select m, ob, sum(trips) origin_trips, round(100.0*sum(trips) filter (where db<>ob and db not in ('Unknown','N/A'))/sum(trips),2) as outbound_excl_unresolved_pct, round(100.0*sum(trips) filter (where db<>ob)/sum(trips),2) as outbound_incl_pct from base group by 1,2 order by 1,3 desc`
- The population the outbound share is measured over, both scopes: 1,235 trips touch a non-NYC borough, 1,000 touch an unresolved one, 94,723 are NYC-borough to NYC-borough — `select count(*) filter (where not o.is_nyc or not d.is_nyc) as pairs_touching_non_nyc, count(*) filter (where o.borough_name in ('Unknown','N/A') or d.borough_name in ('Unknown','N/A')) as pairs_touching_unresolved, count(*) filter (where o.is_nyc and d.is_nyc) as nyc_only_pairs from core.fct_trip f join core.dim_zone o on f.pickup_zone_key = o.zone_key join core.dim_zone d on f.dropoff_zone_key = d.zone_key where f.pickup_datetime >= date '2024-01-01' and f.pickup_datetime < date '2024-04-01' and f.is_billable`
- Revenue is the billable total, not the recognised-revenue total: of 95,958 billable Q1 trips, 1,287 are paid by `Dispute` or `No charge`, worth 31,310.45 of 2,625,634.75 — `select sum(f.total_amount) as billable_revenue, sum(f.total_amount) filter (where p.counts_as_revenue is false) as non_revenue_total, count(*) filter (where p.counts_as_revenue is false) as non_revenue_trips from core.fct_trip f join core.dim_payment_method p on f.payment_method_key = p.payment_method_key where f.pickup_datetime >= date '2024-01-01' and f.pickup_datetime < date '2024-04-01' and f.is_billable`, with the per-method split from `select p.payment_method_name, p.counts_as_revenue, count(*) trips, sum(f.total_amount) revenue from core.fct_trip f join core.dim_payment_method p on f.payment_method_key = p.payment_method_key where f.pickup_datetime >= date '2024-01-01' and f.pickup_datetime < date '2024-04-01' and f.is_billable group by 1,2 order by 3 desc`
- The semantic layer can already express this grain, so the aggregate source is honest and no new metric is needed: a query for `billable_trip_count` grouped by the pickup and dropoff borough levels compiles against `LTS1_detail` (the trips star), and every aggregate source is rejected — `python3 .agents/skills/semantic-model/scripts/ossie.py compile logical-model/nyc_taxi_analytics.ossie.yaml /tmp/ossie_probe/q.json`, exit 0, source `LTS1_detail`, rejecting `LTS2_zone_day_agg`, `LTS3_zone_daypart_dow` and `LTS7_daily_zone_revenue` because "`'zone'` is versioned; rolling it up from an aggregate needs the fact's date".

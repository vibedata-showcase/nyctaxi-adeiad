## Findings

- **Closed by `D-11`.** The finding that returned this intent at `e4ada63` — `resolved_trip_count` and `cross_borough_trip_count` publishing `0` beside cells holding `484`–`3,784` resolved-destination trips — no longer holds. All six unresolved origin-months publish their real basis, keep `0` crossings and a null share, and `assert_borough_flow_unresolved_origin_basis` fails the pre-fix values, so the correction is covered rather than merely applied (`## Coverage`, two `D-11` rows).
- **ADR 0018 states an arithmetic rule the table does not satisfy.** `docs/adr/0018-borough-flows-carry-no-volume-floor.md`, `## Consequences`: "Summing a single origin's rows reproduces that borough's trips, and its off-diagonal rows reproduce the cross-borough denominator." The first clause holds (`rowsum_vs_alltrips_mismatch: 0` over `24` origin-months). The second does not: an origin's off-diagonal **resolved** cells are its trips to a different resolved borough, which is `cross_borough_trip_count`, the **numerator**; the denominator `resolved_trip_count` is the diagonal *plus* those cells. The two agree on only the six unresolved origin-months, where the diagonal is empty by construction. Measured over `24` origin-months: off-diagonal equals the numerator on `18`, equals the denominator on `6`; Manhattan January is `143,904` against `2,640,103`. ADR 0019's own sentence states the correct rule ("an origin's published diagonal plus its off-diagonal resolved cells reproduce the share's denominator"), so the two ADRs this intent wrote contradict each other, and the ADR 0018 wording would have a reader check the denominator against the wrong set of cells. — `with per as (select month_start_date, origin_borough, max(resolved_trip_count) as denominator, max(cross_borough_trip_count) as numerator, coalesce(sum(trip_count) filter (where dest_borough <> origin_borough and not dest_is_unresolved),0) as offdiag, coalesce(sum(trip_count) filter (where dest_borough = origin_borough and not dest_is_unresolved),0) as diag from agg.agg_borough_flow_monthly group by 1,2) select count(*) as origin_months, count(*) filter (where offdiag = numerator) as offdiag_equals_numerator, count(*) filter (where offdiag = denominator) as offdiag_equals_denominator, count(*) filter (where diag + offdiag = denominator) as diag_plus_offdiag_equals_denominator from per`
- **ADR 0019's illustrative inflation figure does not follow from the change it describes.** The rejected option is "Count any differing destination borough as a crossing", which changes the numerator only; on the ADR's own published denominator that takes Manhattan's January share from `5.4507%` to `5.86%`, not `5.83%`. `5.83%` is reproducible only by also swapping the denominator to all of the origin's trips (`154,657 / 2,650,856`), a change the option does not state. The decision and its rule are right and the direction of the effect is right; the figure's denominator is the mismatch. — `with man as (select max(resolved_trip_count) as denominator, max(cross_borough_trip_count) as cross_count, sum(trip_count) filter (where dest_is_unresolved) as unresolved_cells, sum(trip_count) as all_cells from agg.agg_borough_flow_monthly where month_start_date='2024-01-01' and origin_borough='Manhattan') select denominator, cross_count, unresolved_cells, all_cells, round(100.0*cross_count/denominator,2) as published, round(100.0*(cross_count+unresolved_cells)/denominator,2) as counterfactual_same_denominator, round(100.0*(cross_count+unresolved_cells)/all_cells,2) as counterfactual_all_trips from man` → `2,640,103 / 143,904 / 10,753 / 2,650,856 / 5.45 / 5.86 / 5.83`.
- **Both findings are text-only and both live in ADRs this intent wrote**, so this returns to `requirement`, where `domain-modeling` corrects the two sentences against these measurements. No SQL, contract, test or column changes: every data gate and every promise in `## Coverage` holds at `0594ce6`, and the `D-11` correction that was the object of this run is complete and covered.

The relation publishes `0` for both counts on all six of those origin-months, which the `## Findings` row records. — `select o.borough_name as origin_borough, count(*) as billable_trips, count(*) filter (where not dz.is_unresolved_zone) as trips_with_resolved_dest, count(*) filter (where not dz.is_unresolved_zone and o.borough_name != dz.borough_name) as cross from core.fct_trip f join core.dim_zone o on f.pickup_zone_key = o.zone_key join core.dim_zone dz on f.dropoff_zone_key = dz.zone_key where f.pickup_datetime >= timestamp '2024-01-01' and f.pickup_datetime < timestamp '2024-02-01' and f.is_billable and o.is_unresolved_zone group by 1 order by 1`

## Open questions

1. **`mart_daily_zone_revenue.trip_count` carries a wrong description, and correcting it needs a semantic-model decision.** `odcs.py generate` owns that column's dbt description and derives it from the Ossie field the column binds, overwriting hand-written text and ignoring a description added to the contract. The generated sentence is `Trips, billable or not.` while the column counts billable trips only (it sums to 95,958, against 97,184 in-window trips). The cause is that the column name `trip_count` resolves to the population-wide `trip_count` metric before `LTS7_daily_zone_revenue`'s honest binding of that column to `billable_trip_count`. The same name on `agg_trip_zone_daily` genuinely is the population-wide column, so the two cannot both be served by one resolution rule. Design decision `D-06` promised this correction and `D-08` records why it could not be carried out here. It was already wrong before this intent; the value is unchanged. Settling it changes how a shared column name resolves to a metric, which is a semantic-layer decision the Requirement did not ask for.

## Discovery

Written by designing, from the Domain warehouse before any model changed. Every figure below is a measurement, so it lives here and not in a design record.

- **The two relations do not currently agree, and the gap is exactly the non-billable trips.** `finance.mart_daily_zone_revenue` Q1 2024 returns 7,961 rows, 95,958 trips, 2,629,185.82 revenue; `agg.agg_trip_zone_daily` returns 7,997 rows, 97,184 trips, 2,597,120.92. `core.fct_trip` over the same window holds 97,184 trips of which 95,958 are billable, with 2,597,120.92 over all trips and 2,629,185.82 over billable ones. The report therefore counts only billable trips, and the aggregate counts all of them.
  - `select sum(trip_count) as trips, round(sum(total_revenue),2) as revenue from finance.mart_daily_zone_revenue where trip_date >= date '2024-01-01' and trip_date < date '2024-04-01'` → `95958 | 2629185.82`
  - `select sum(trip_count) as trips, round(sum(total_revenue),2) as revenue from agg.agg_trip_zone_daily where pickup_date >= date '2024-01-01' and pickup_date < date '2024-04-01'` → `97184 | 2597120.92`
  - `select count(*) as all_trips, count(*) filter (where is_billable) as billable_trips, round(sum(total_amount),2) as all_revenue, round(sum(total_amount) filter (where is_billable),2) as billable_revenue from core.fct_trip where pickup_date >= date '2024-01-01' and pickup_date < date '2024-04-01'` → `97184 | 95958 | 2597120.92 | 2629185.82`

- **JFK Airport, which the request names.** The report's figure and the aggregate's differ for the same reason.
  - `select sum(trip_count) as trips, round(sum(total_revenue),2) as revenue from finance.mart_daily_zone_revenue where trip_date >= date '2024-01-01' and trip_date < date '2024-04-01' and zone_name = 'JFK Airport'` → `4120 | 337711.05`
  - `select sum(trip_count) as trips, round(sum(total_revenue),2) as revenue from agg.agg_trip_zone_daily where pickup_date >= date '2024-01-01' and pickup_date < date '2024-04-01' and zone_name = 'JFK Airport'` → `4261 | 329766.06`

- **The aggregate cannot supply the report's columns today.** `agg.agg_trip_zone_daily` has 14 columns: `pickup_date_key`, `pickup_date`, `pickup_location_id`, `zone_name`, `borough_name`, `trip_count`, `total_revenue`, `total_miles`, `attributed_driver_count`, `prev_day_trip_count`, `same_day_last_week_trip_count`, `trip_count_7d_avg`, `revenue_28d_rolling`, `revenue_rank_that_day`. It has no billable-only measure of any kind, no `fare_revenue`, `tip_revenue`, `surcharge_revenue` or `toll_revenue`, and no `reporting_region`. So R-01 cannot be met by a re-point alone.
  - `select column_name, data_type from information_schema.columns where table_schema='agg' and table_name='agg_trip_zone_daily' order by ordinal_position`

- **The extension reproduces the request's four acceptance figures exactly, at the report's own row count.** Computing the report's measures from `core.fct_trip` with `filter (where is_billable)` and dropping zone-days with no billable trip returns 7,961 rows, 95,958 trips, 2,629,185.82 revenue, and 4,120 trips / 337,711.05 revenue for JFK Airport — all four numbers the request states. This is the design's central feasibility check.
  - `with proposed as (select f.pickup_date, z.zone_natural_key as pickup_location_id, z.zone_name, f.pickup_date_key, count(*) filter (where f.is_billable) as billable_trip_count, sum(f.fare_amount) filter (where f.is_billable) as billable_fare_revenue, sum(f.tip_amount) filter (where f.is_billable) as billable_tip_revenue, sum(f.total_surcharges) filter (where f.is_billable) as billable_surcharge_revenue, sum(f.tolls_amount) filter (where f.is_billable) as billable_toll_revenue, sum(f.total_amount) filter (where f.is_billable) as billable_total_revenue from core.fct_trip f join core.dim_zone z on f.pickup_zone_key = z.zone_key where f.pickup_datetime >= timestamp '2024-01-01' and f.pickup_datetime < timestamp '2024-04-01' group by 1,2,3,4 having count(*) filter (where f.is_billable) > 0) select (select sum(billable_trip_count) from proposed), (select round(sum(billable_total_revenue),2) from proposed), (select sum(billable_trip_count) from proposed where zone_name='JFK Airport'), (select round(sum(billable_total_revenue),2) from proposed where zone_name='JFK Airport'), (select count(*) from proposed)` → `95958 | 2629185.82 | 4120 | 337711.05 | 7961`

- **R-02's cell-for-cell equality is achievable, not merely approximate.** Comparing the proposed measures against the shipped `finance.mart_daily_zone_revenue` on `(trip_date, pickup_location_id)` with `is distinct from` — the strictest comparison, catching a 1-ulp float difference — returns zero differences on all six measures across all 7,961 rows. Summing with a `filter` clause yields the identical floating-point result as summing over a pre-filtered population, so no rounding tolerance is needed.
  - `with proposed as (select f.pickup_date, z.zone_natural_key as pickup_location_id, count(*) filter (where f.is_billable) as trip_count, sum(f.fare_amount) filter (where f.is_billable) as fare_revenue, sum(f.tip_amount) filter (where f.is_billable) as tip_revenue, sum(f.total_surcharges) filter (where f.is_billable) as surcharge_revenue, sum(f.tolls_amount) filter (where f.is_billable) as toll_revenue, sum(f.total_amount) filter (where f.is_billable) as total_revenue from core.fct_trip f join core.dim_zone z on f.pickup_zone_key = z.zone_key where f.pickup_datetime >= timestamp '2024-01-01' and f.pickup_datetime < timestamp '2024-04-01' group by 1,2) select count(*) filter (where p.trip_count is distinct from m.trip_count) as trip_count_diff, count(*) filter (where p.fare_revenue is distinct from m.fare_revenue) as fare_diff, count(*) filter (where p.tip_revenue is distinct from m.tip_revenue) as tip_diff, count(*) filter (where p.surcharge_revenue is distinct from m.surcharge_revenue) as surcharge_diff, count(*) filter (where p.toll_revenue is distinct from m.toll_revenue) as toll_diff, count(*) filter (where p.total_revenue is distinct from m.total_revenue) as total_diff, count(*) as joined_rows from proposed p left join finance.mart_daily_zone_revenue m on p.pickup_date = m.trip_date and p.pickup_location_id = m.pickup_location_id where p.trip_count > 0` → `0 | 0 | 0 | 0 | 0 | 0 | 7961`

- **The zone labels already agree, so no dimension label can drift.** Joined on `(date, pickup_location_id)`, the two relations disagree on `zone_name` for 0 rows and on `borough` / `borough_name` for 0 rows. Both read the same `dim_zone` version resolved per trip, so carrying the aggregate's labels into the report changes no cell.
  - `with f as (select trip_date, pickup_location_id, zone_name, borough from finance.mart_daily_zone_revenue), a as (select pickup_date, pickup_location_id, zone_name, borough_name from agg.agg_trip_zone_daily) select (select count(*) from f join a on f.trip_date=a.pickup_date and f.pickup_location_id=a.pickup_location_id where f.zone_name is distinct from a.zone_name) as zone_name_diffs, (select count(*) from f join a on f.trip_date=a.pickup_date and f.pickup_location_id=a.pickup_location_id where f.borough is distinct from a.borough_name) as borough_diffs` → `0 | 0`

- **Adding `reporting_region` does not break the aggregate's grain.** Grouping the same population by `(pickup_date, pickup_location_id, zone_name, borough_name, reporting_region)` still yields 7,997 rows and 7,997 distinct `(pickup_date, pickup_location_id)` pairs, because `reporting_region` is functionally dependent on the zone. The new column is safe to add to the existing `group by` without splitting a row.
  - `select count(*) as rows_with_region_added, count(distinct (pickup_date, pickup_location_id)) as distinct_grain from (select f.pickup_date, z.zone_natural_key as pickup_location_id, z.zone_name, z.borough_name, z.reporting_region from core.fct_trip f join core.dim_zone z on f.pickup_zone_key = z.zone_key where f.pickup_datetime >= timestamp '2024-01-01' and f.pickup_datetime < timestamp '2024-04-01' group by 1,2,3,4,5) t` → `7997 | 7997`

Those 36 are exactly the zone-days whose trips are all non-billable.
  - `select (select count(*) from f anti join a on f.trip_date=a.pickup_date and f.pickup_location_id=a.pickup_location_id) as in_finance_not_agg, (select count(*) from a anti join f on f.trip_date=a.pickup_date and f.pickup_location_id=a.pickup_location_id) as in_agg_not_finance` → `0 | 36` (with `f` and `a` as the two relations' grains)

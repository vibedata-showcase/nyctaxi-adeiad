## Discovery

Design-time profiling of the inputs the new model reads, and of the anchors a claim of closure needs. Every number below is a query run in this session against `target: "domain"` (the Domain warehouse, read-only); the sandbox was not written.

- `fct_trip` is the fact; the billable in-window population and its monthly anchors are self-consistent — `select date_trunc('month', pickup_datetime) as m, count(*) as trips, sum(case when is_billable then 1 else 0 end) as billable, min(pickup_datetime) as mn, max(pickup_datetime) as mx from core.fct_trip group by 1 order by 1` returned 2024-01: 30,369 trips / 29,985 billable (first 2024-01-01T00:05:25, last 2024-01-31T23:53:18); 2024-02: 30,402 / 30,017; 2024-03: 36,413 / 35,956. Verdict: **Ready**.
- the reporting window is fully covered, so no month is cut short — `select count(distinct pickup_date) as days, min(pickup_date) as first_day, max(pickup_date) as last_day from core.fct_trip where pickup_date >= date '2024-01-01' and pickup_date < date '2024-04-01'` returned 91 days, 2024-01-01 to 2024-03-31.
- the billable in-window totals the table must close to are 95,958 trips and 2,629,185.82 revenue — `select count(*) as billable_trips, round(sum(total_amount),2) as billable_revenue, count(*) filter (where total_amount = 0) as zero_totals, count(*) filter (where total_amount is null) as null_totals, count(*) filter (where pickup_date is null) as null_dates from core.fct_trip where is_billable and pickup_datetime >= timestamp '2024-01-01' and pickup_datetime < timestamp '2024-04-01'` returned 95,958 / 2,629,185.82 / 0 / 0 / 0. Verdict: **Ready**.
- `dim_zone` has one row per zone key, so neither role's join fans out — `with f as (select pickup_zone_key, dropoff_zone_key from core.fct_trip where is_billable and pickup_datetime >= timestamp '2024-01-01' and pickup_datetime < timestamp '2024-04-01') … select (select count(*) from z) as zone_rows, …` returned 272 zone rows, 272 distinct zone keys, 95,958 trips, and 95,958 rows after each join and after both joins. Verdict: **Ready**.
- every billable in-window trip resolves both zone keys, so nothing is lost to either join — the same query's `null_pu = 0`, `null_do = 0`, `null_any = 0` over 95,958 billable in-window trips. Only the *unresolved* zones (zones whose borough is `Unknown` or `N/A`) need the coalesce; a null key does not occur today and is still handled. Verdict: **Ready**.
- `dim_zone.borough_name` carries eight values, of which two place no zone in a borough — `select borough_name, reporting_region, is_nyc, count(*) as zones from core.dim_zone where is_current_version group by 1,2,3 order by 1` returned Bronx / Brooklyn / Manhattan / Queens / Staten Island (is_nyc true, 43/61/69/69/20 zones), EWR (is_nyc false, "Out of State", 1 zone), and N/A and Unknown (is_nyc false, "Unresolved", 1 zone each). `is_unresolved_zone` is exactly the last two.
- `dim_date` resolves every billable in-window trip, so keying the month off the calendar loses nothing — `with f as (select pickup_date_key, pickup_date from core.fct_trip where is_billable and …) select count(*) as trips, count(*) filter (where pickup_date_key is null) as null_key, count(*) filter (where d.date_key is null) as unmatched, count(distinct d.month_start_date) as months from f left join core.dim_date d on f.pickup_date_key = d.date_key` returned 95,958 / 0 / 0 / 3.
- the semantic compiler already groups one measure by both zone roles, which is the shape the new source declares — `semantic_query` in `sql` mode with `billable_trip_count`, grouped by `trips_to_date` month, `trips_to_pickup_zone` borough and `trips_to_dropoff_zone` borough, resolved to source `LTS1_detail` and emitted `left join dim_zone as d1 … left join dim_zone as d2` with `group by 1, 2, 3`.
- the pass-through the excluded `unresolved` group relies on is already reconciled in the domain — a full join of `agg.agg_weather_demand_daily` against a detail recomputation on (obs_date, borough_name) returned 0 differing groups, so a sentinel no borough level declares passes the content test while `assert_semantic_levels_hold` reports it.
- the size of the population under a floor, used in ADR 0018's reasoning — 104 populated (month, origin borough, destination borough) cells, 51 of them under 25 billable trips, holding 179 trips and 13,058.48 revenue.
- quality verdicts do occur among the billable in-window trips, so "no verdict filters a trip" is a real decision rather than an idle one — `select count(*) as billable_q1, count(*) filter (where q.is_zero_distance) … from core.fct_trip f join core.dim_trip_quality q on f.trip_quality_key = q.trip_quality_key where f.is_billable and f.pickup_datetime >= timestamp '2024-01-01' and f.pickup_datetime < timestamp '2024-04-01'` returned 95,958 billable trips, of which 2,204 have zero distance, 864 are implausibly short, 39 implausibly fast, 1 has a negative duration, 7,439 come from a sparse vendor feed, 1,102 carry an undocumented rate code, 360 touch an unresolved pickup zone, and 2,719 are not `is_clean_trip`.

## Findings

- **A remapped star-member description is derived from the wrong Ossie field, and `check` cannot see it.** `odcs.py generate` writes a star member's column description from the `datasets[].fields[]` entry whose name equals the physical column name. `mart_daily_zone_revenue.trip_count` is the billable count, bound in the `column_map` to `billable_trip_count`, but the field named `trip_count` in the `trips` dataset is the all-trips metric, so `generate` wrote "Trips, billable or not." and `check` reported nothing stale because that is exactly what it would write. The column contradicted `R-07` and the built SQL. Fixed at `8d228e0` with a `{{ doc("daily_zone_revenue_trip_count") }}` pointer — the escape hatch the `data-contract` skill names for a pointer that is left alone — and proven to render by `dbt docs generate` then reading `target/catalog.json`. Recorded for the plugin's maintainers: this gap is in `odcs.py`'s description source, not in this repository.
- **The compiler will not use the ops aggregate for a query whose filter does not imply its `content_filter`.** `LTS2_zone_day_agg`'s `content_filter` names `NOT pickup_zone_key IS NULL`, but `agg_trip_zone_daily` has no `pickup_zone_key` column (it carries `pickup_location_id`), so a caller cannot write that predicate in the model's expression language. A correct query still gets the right answer from `LTS1_detail`; it simply does not use the new source unless the filter names a column the aggregate does not have. `assert_semantic_content_holds` holds the binding on data (7,997 groups, 0 real differences, the 36 zero-billable groups the only divergence, as null-vs-zero), so the mapping is honest — the reach is narrower than it reads. Recorded, not fixed: changing `content_filter` changes what the source claims to answer, which is a design decision, not a verification repair.
